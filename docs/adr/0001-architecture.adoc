= ADR-0001. Архитектура MVP

Статус:: Принято
Дата:: 2026-11-06

== Контекст

Нужно выпустить MVP мобильного приложения для Android силами одного-двух разработчиков. Ожидается до 1000 пользователей в первый год. Стоимость поддержки — до 20 долларов в месяц, максимум 30. Данные пользователей чувствительные и относятся к российским пользователям.

== Решение

* Архитектура — монолит: один бэкенд-сервис на одном сервере, запуск в Docker.
* Бэкенд — Python 3.12 и FastAPI.
* Основная база данных — PostgreSQL на том же сервере.
* Мобильный клиент — Kotlin и Jetpack Compose, локальная база Room для офлайн-режима.
* Вход — только через учётную запись Google.
* ИИ-сервис — российский провайдер: GigaChat API или Yandex AI Studio; выбор после тестирования. Обращение к ИИ — через отдельный модуль-адаптер.
* Отдельный кеш (Redis) и очередь задач в MVP не используются. Еженедельные отчёты запускаются встроенным планировщиком (APScheduler), ограничения частоты запросов — на обратном прокси.
* Хостинг и бэкапы — у российского провайдера.

== Рассмотренные альтернативы

* Микросервисы — избыточны для объёма MVP и команды из одного-двух человек.
* Redis для кеша и лимитов — не нужен при ожидаемой нагрузке; добавляется позже при росте.
* Зарубежные ИИ-сервисы и хостинг — исключены из-за трансграничной передачи персональных данных.

== Последствия

* Простое развёртывание и низкая стоимость поддержки.
* Масштабирование ограничено одним сервером; при росте нагрузки потребуется пересмотр (вынос базы, Redis, несколько экземпляров бэкенда).
* Лимиты вынесены в отдельный модуль, чтобы при необходимости заменить хранилище счётчиков без изменения остального кода.
